# x402 premium data

LedgerMind has two separate payment paths: browser-wallet purchases in the dashboard and Binance Agentic Wallet purchases in the backend task runner.

## Browser-wallet flow

The dashboard uses RainbowKit with wagmi and viem. The analyzed public address is independent of the paying wallet. Standard reports remain available without connecting a wallet.

1. Run an analysis or open a saved report.
2. In Premium, connect a wallet and select a supported report asset.
3. Get a quote. Switch to Base if needed. The backend verifies wallet type, USDC balance, resource, recipient, network, amount, and token domain against the pinned CoinMarketCap policy.
4. Review the quote and select **Confirm & pay 0.01 USDC**. The wallet displays an EIP-712 `TransferWithAuthorization` signature request for a single-use USDC authorization.
5. The backend verifies the signer against the stored quote, atomically records submission, and sends the x402 `PAYMENT-SIGNATURE` envelope to the merchant once.
6. The UI loads the merchant receipt, transaction link, and returned CMC metrics. A Markdown supplement can be exported independently of the original report.

The currently pinned policy is 0.01 USDC on Base for a CMC quote. Changed merchant requirements are rejected rather than silently accepted. Supported report symbols are ETH, BTC, BNB, and SOL; the treasury report must actually include the chosen asset or its supported wrapped ticker.

### Configuration

Copy [.env.example](../../.env.example) to `.env` if customization is needed:

```dotenv
BROWSER_PREMIUM_ENABLED=true
WALLETCONNECT_PROJECT_ID=
MAX_PAYMENT_USD=0.10
MAX_TASK_BUDGET_USD=1.00
DAILY_BUDGET_USD=1.00
```

Browser extension wallets work without a project ID. For WalletConnect mobile QR, obtain a public project ID from the [Reown dashboard](https://dashboard.reown.com), set `WALLETCONNECT_PROJECT_ID`, and restart the server. Do not use a private API key or wallet seed in that field.

Browser payments do not require `BAW_CLI_JS`, a model API key, or `PAYMENT_MODE=binance`. `BROWSER_PREMIUM_ENABLED` is an independent gate: set it to `false` to disable new browser quotes and submissions. Every payment still requires a signature in the user's wallet. Only standard EOA wallets are currently supported; contract wallets fail preflight with an explicit message.

The per-payment and per-task limits must cover the quote. The browser daily cap is tracked per paying wallet across its persisted purchases; it does not use `MOCK_WALLET_USD` as an onchain balance.

### State, persistence, and recovery

| State | Meaning |
| --- | --- |
| `quoted` | Wallet balance and merchant terms passed preflight; nothing submitted. |
| `submitting` | The authorization has been claimed for submission. A second request cannot replay it. |
| `settled` | Merchant reported a matching successful receipt and valid data was saved. |
| `paid_data_unavailable` | Merchant confirmed payment but the data could not be delivered or validated. Receipt retained. |
| `unknown` | Settlement cannot be established, including a server restart during submission. No automatic recharge. |

Purchases are keyed by report, payer, and asset in SQLite. Expired unsigned quotes can be replaced. Submitted, settled, or uncertain purchases cannot be recreated for that same combination. Refresh status or reopen the saved report to recover the recorded result. If a purchase remains unknown, inspect the paying wallet and merchant before any further payment; the UI does not claim it is unpaid.

Signatures are kept only in memory for submission, not in the database, audit log, or browser storage. Quote authorization fields, purchase state, validated data, and receipt metadata are persisted. The receipt is merchant evidence; it is not an independent RPC verification of settlement. Premium supplements do not rewrite the original report hash or balances.

### API

Premium POST requests require the same-origin `X-LedgerMind-Token` returned by `/api/config`.

| Endpoint | Input / result |
| --- | --- |
| `POST /api/premium/quote` | `{ reportId, payer, symbol }` → persisted quote or existing purchase. |
| `POST /api/premium/purchases/:id/pay` | `{ signature }` → recorded purchase status. |
| `GET /api/premium/purchases?reportId=...` | List report-linked purchases and supplements. |
| `GET /api/premium/purchases/:id` | Recover one purchase's status and receipt/data. |

The app is a local loopback service with host and origin checks. RainbowKit connection is not account authentication for a public multi-user deployment.

## Backend Agentic Wallet flow

Legacy task APIs can still use the Binance Agentic Wallet adapter. This path signs with the wallet configured on the backend host, not the browser wallet.

```dotenv
PAYMENT_MODE=binance
REAL_PAYMENTS_ENABLED=true
BAW_CLI_JS=C:/absolute/path/to/@binance/agentic-wallet/dist/index.js
MAX_PAYMENT_USD=0.01
DAILY_BUDGET_USD=0.50
MAX_TASK_BUDGET_USD=0.01
```

Use [.env.live.example](../../.env.live.example), configure the wallet and selected model provider, then run:

```sh
npm run setup:live
npm run check:live
npm run build
npm run start:live
```

`check:live` checks wallet status, merchant requirements, and preview without signing or paying. `npm start` does not automatically load `.env.live`.

The treasury API's legacy `usePremiumData` / `authorizePremiumPayment` fields may queue an Agentic Wallet task and return `premiumData.taskId`. A queued task does not establish settlement. The new dashboard uses the browser premium endpoints instead of those checkboxes.

## Verification

`npm test` covers signatures, pinned merchant terms, expiry, balance failures, concurrent submissions, receipt validation, data delivery failures, and restart recovery for the browser flow alongside the existing backend tests.

`node --import tsx backend/scripts/verify-premium-ui.ts` exercises RainbowKit connection, Base switching, quote review, rejected and accepted test signatures, receipt rendering, reload recovery, and mobile layout with a mock wallet and merchant responses. Like the standard UI checker, it expects Chrome at the configured Windows path. These tests never spend real funds and do not establish live merchant availability.
